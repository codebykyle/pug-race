Page self-check — a tripwire, not proof

A browser extension can rewrite any script on a page. This panel hashes the race algorithm's own source text, so if anything patched it, the fingerprint changes. Read the limits below — this is a tripwire, not a proof.

What this cannot do. A page cannot disable extensions — they run at higher privilege than page scripts, and a determined hostile extension shares this execution context and could fake this panel too. The check that cannot be faked is an independent verifier recomputing the race on a clean machine: a rigged page publishes results that no honest recomputation reproduces. Verify on a second device and extension tampering is caught regardless of what ran on the operator's laptop. To actually run extension-free, launch the browser with --disable-extensions (see launch-clean.sh), or use a Guest profile.

Verify without this page

The guarantee doesn't depend on this page at all. verify.js is a standalone Node script (no packages, no network) that recomputes the race from a receipt and runs the same checks:

node verify.js receipt.json --saw <the commitment you saw>

Get it from the project's source, or from /verify.js on the race server — it's short enough to read. The algorithm inside is a verbatim copy of this page's, and it prints the same build fingerprint, so a matching fingerprint means you ran the same code. It also checks its SHA-256 against Node's own.

Why this race cannot be rigged

The whole race is a pure function of one value: the final seed. There is no randomness anywhere else — no Math.random(), no clock, no mouse position, no network call. Same seed in, same race out, on any machine, forever. So the only question a sceptic needs answered is: could anyone have chosen the seed to make their friend win? The seed comes from a commit–reveal between the operator and the audience:

1
The operator commits first — to everything. The roster, the race length and where the audience value will come from are finalised, a 256-bit secret is generated with crypto.getRandomValues, and a SHA-256 fingerprint of all four together is published. Changing any of them afterwards — even slipping an invisible character into one name — changes the fingerprint, and finding a different input with the same fingerprint is a preimage attack on SHA-256 that nobody can do.
2
The roster goes public. Every viewer's screen shows the sealed name list in the lobby and checks it reproduces the sealed roster hash, so a field padded with extra entries for one person is visible before the audience speaks.
3
The audience commits second. After the fingerprint has been public for at least 20 seconds, the crowd supplies a value from the source named in advance, so the operator can't pick whichever of several shouted answers suits them. The operator chose the secret without knowing this value and can no longer change it.
4
Neither side controls the result. Final seed = SHA-256(secret | audience value). To rig it the operator would have to predict the audience value; the audience would have to know the secret. So the seed is fair as long as at least one of the two parties is honest.
5
Every race is checked before it plays. Once the audience value is fixed the secret protects nothing, so it is sent with the race announcement. The server refuses a race that doesn't match its commitment, and every viewer's page re-checks it independently and refuses to play a race that fails.
6
Anyone can re-check it later. The receipt holds everything needed to recompute the race. The Verify tab, the standalone verify.js, or any SHA-256 tool reproduces it exactly and confirms it matches the fingerprint people saw on screen before the race.

A race, step by step

What actually happens, in order, when a race is run live through the race server. Local races on a file:// copy follow the same steps without the server.

  1. Host signs in. The setup page is locked until the host password is proven at POST /api/unlock. The check is constant-time and rate-limited on the server, so editing the page can't bypass it. The server then hands back the operator key that every operator call needs. Nothing secret is in the URL, so the screen is safe to share.
  2. Roster and length. Names are pasted (2–10,000, separated by new lines, commas, semicolons or tabs) and cleaned as they're parsed (see Names below). Names that look alike block the next step. The length is 10–600 seconds.
  3. Entropy source. The operator writes down where the audience value will come from, e.g. “the first word shouted after I say go”, or ticks Viewers submit it on the watch page. It is sealed into the commitment word for word.
  4. Generate secret seed. A fresh 256-bit secret is drawn and the commitment is computed. The page seals the roster, length and source: editing any of them afterwards discards the commitment, and a new one must be generated and shown again.
  5. Lobby. The commitment and the full sealed roster go to POST /api/lobby. The server logs the time it was published. Every viewer on /watch sees the commitment and the roster, their page records when it first saw that commitment, and it checks that the roster reproduces the sealed hash. If the commitment is later replaced, every screen shows a “commitment replaced” alert.
  6. 20-second wait. The operator page won't start a real race until the commitment has been public for 20 seconds, and the server enforces the same minimum. This gives the audience time to photograph it.
  7. Audience value. Collected from the named source and typed in publicly. The page shows “Hashed as: …”, the cleaned form that actually goes into the seed. With viewer submissions, the operator instead opens and closes submissions, and the value is combined from what viewers sent (see Viewer submissions below).
  8. Announcement. POST /api/race carries the seed, roster, length, secret, entropy source and audience value. The server refuses it unless the commitment is the one in the lobby, has been public for 20 seconds or more, hasn't been raced before, and is reproduced by the secret, roster, length and source. The seed must also be SHA-256(secret | audience value).
  9. Viewer pre-flight. Each viewer's page runs the same checks against what it saw in the lobby. A race that passes shows “✓ checked before the start” and fills in the Verify tab at once. One that fails is not played and shows “✗ race refused”.
  10. Countdown and race. A 30-second countdown on every screen lets late joiners catch up, then the gun. The result was already computed in full at the announcement; the animation is playback.
  11. Receipt. The operator hits Reveal. POST /api/receipt is refused unless it matches the race viewers were shown. The server attaches its own timeline for the commitment as receipt.server, and the receipt is pushed to every viewer.

Practice races skip the commitment, are marked “PRACTICE — not a real race, results don't count” on every screen, and fail verification if anyone tries to pass one off as real.

The exact formulas

Everything is standard SHA-256 over UTF-8 text, written as lowercase hex. | is a literal pipe character with no spaces around it.

rosterHash = SHA-256( sorted keys joined by "\n" ) commitment = SHA-256( "pug-race/2|" + secret + "|" + rosterHash + "|" + raceLengthSeconds + "|" + entropySource ) finalSeed = SHA-256( secret + "|" + audienceSeed ) submission = SHA-256( "pug-race/sub|" + commitment + "|" + salt + "|" + text ) (viewer submissions only) audienceSeed = revealed texts, in submission-hash order, joined by " | " (viewer submissions only) racer RNG = xoshiro128** seeded from SHA-256( finalSeed + "|" + key ) obstacles = xoshiro128** seeded from SHA-256( finalSeed + "|obstacles" ) resultsHash = SHA-256( lines of place + "|" + key + "|" + time to 4 decimals , joined by "\n" )
  • Keys. Names are sorted by UTF-16 code unit (not by locale, which differs between machines). The first copy of a name is its own key; repeats become Bean#1, Bean#2… The list's original order plays no part.
  • Unambiguous fields. The secret and roster hash are fixed-length hex and the length is an integer, so the entropy source is simply the rest of the string. No two different inputs join to the same text.
  • RNG. xoshiro128** takes its four 32-bit words from the first 32 hex characters of the hash. Normal deviates are the sum of four uniforms (Irwin–Hall), scaled by √3, which needs only + − ×.
  • Format tag. pug-race/2 is written into the commitment, so a format 2 commitment can never be confused with any other hash. Older format 1 receipts committed only to SHA-256(secret) and are shown as not provably fair.

Names

Two names that look the same must be the same, or an operator could hide variants of one entrant. Every name is cleaned before it's counted or hashed:

  • NFKC normalisation folds fullwidth letters, ligatures and styled maths letters into plain ones.
  • Invisible characters are removed: Unicode's default-ignorable set (zero-width spaces and joiners, bidi controls, fillers, variation selectors, tags), plus format, control, unassigned, private-use and lone-surrogate code points, and a few symbols that render blank. An emoji keeps its own presentation selector.
  • Whitespace of every kind becomes one ordinary space, trimmed at both ends.
  • A trailing #<digits> gets a space (Table #3 → Table # 3), because #1, #2… is how repeats are keyed. Without this, [Bean, Bean] and [Bean, Bean#1] would hash the same.
  • Look-alikes block the commitment. Different names that look identical, through Cyrillic, Greek, Armenian or Cherokee letters, small capitals, I/l/1, O/0, or rn/m, vv/w, cl/d, must be renamed first. Names mixing alphabets get an ⓘ marker.
  • Exact repeats are allowed. Each copy races separately, with its own key. The lobby and the verifier both list them (“Bean ×3”), so everyone can see how many entries each name has.

The audience value

The operator types what the audience said, so text that only looks the same must hash the same. It is cleaned like a name, then lower-cased and reduced to letters, digits, accents, symbols (emoji) and single spaces.

  • “Banana!”, “banana.” and “BANANA” all become banana.
  • Punctuation is dropped: 7-4-2 is hashed as 742.
  • The setup page shows Hashed as: … while it's typed, so the room sees exactly what went in.
  • Every viewer's page refuses a race, and the verifier fails a receipt, whose audience value isn't in this cleaned form.

The stronger the audience value, the stronger the guarantee. Name one specific value nobody could know in advance: the first word shouted after “go”, dice rolled on camera, or several people each adding a word. Anything the operator could have known beforehand doesn't count.

Viewer submissions

Instead of one shouted value, everyone on the watch page can add text, and all of it is combined. Open text would let the operator, who knows the secret, send the last submission after trying candidates until their pick wins. So submissions are sealed first and revealed after:

  1. Open. The operator opens submissions. Each viewer's page cleans its text, adds a random salt, and sends only a fingerprint of it, tied to this race's commitment. No one, the server included, can see any text.
  2. Close. The operator closes submissions. The list of fingerprints is frozen and shown to every viewer, whose page remembers it.
  3. Reveal. Each page sends its text automatically (keep the page open). The server accepts a text only if it matches a frozen fingerprint. The reveal ends by itself once everything is in, or after 15 seconds, so no one can stop it at a convenient moment.
  4. Combine. The audience value is the revealed texts in fingerprint order, joined with “ | ”. The race can't use any other value, and each commitment gets one collection.
  • Each viewer's page refuses the race if the record doesn't combine to the race's audience value, if a fingerprint was added after the list was frozen, or if its own submission was left out.
  • The verifier recomputes the combination from the receipt, and warns when submissions were never revealed or only one viewer contributed.
  • The limit: someone holding several sealed submissions can choose which of theirs to reveal, which gives them a few alternative outcomes. That's why unrevealed submissions are counted on every screen. The race is fair as long as at least one submission came from a viewer with nothing to do with the operator, and every viewer's page confirms whether theirs was included.

The race simulation

Each race is simulated in full, from the gun to the last racer home, before the first frame is drawn. These are the rules, with the actual values the code uses.

  • Fixed steps. Physics advances in steps of 0.1 s. The track is length × 0.5 units long, so the winner crosses after roughly the chosen number of seconds.
  • Innate pace. Each racer gets a base speed of 0.5 × (1 + 0.05 × a normal draw), never below 0.4, plus one of 100 skins, both from its own RNG stream.
  • Surges. Speed wanders up and down from step to step (an AR(1) process, coefficient 0.92, spread 0.16), so the lead changes hands. A racer never drops below 0.10, so everyone finishes.
  • Standing start. For the first 2.5 s the whole field eases off the line together (a smooth ramp from 16% to full speed), identical for everyone.
  • Obstacles. Between 3 and 14 of them, spread from 12% to 90% of the way down the track, drawn from the seed: mud puddle, squirrel, dropped snack, butterfly or nap. Every racer that crosses one has the same 26% chance of being slowed (to 22–55% speed for 1.2–2.2 s, depending on the obstacle).
  • Comeback zoomies. A racer more than 3% of the track behind the leader can get a 1.55× burst for 1.8 s, with a 3 s cooldown. The chance per second is 4 × (deficit ÷ track length), capped at 0.75. It depends only on how far behind you are, never on who you are.
  • Photo finish. Each racer's finishing time is interpolated to the exact moment it crossed the line, not rounded to a step. Exact ties are broken by key, so the order is always fully determined.

Why it's fair to every racer

  • Order-independent. A racer's randomness comes from its name and copy number, not its row, so shuffling the list changes nothing and the operator can't fish for a lucky ordering.
  • Identity-blind. No rule ever looks at who a racer is, only where it is. All racers run the same rules at the same odds, so no one can be favoured.
  • Measured. Over 40,000 races of 10, finishing places showed no bias by position or name (chi-square 6.82, 9 degrees of freedom), and skins were uniform.

The trade-off: zoomies depend on the leader's position, so racers aren't fully independent draws. The race is still one deterministic function of the committed seed, verifiable to the last decimal.

Why it reproduces everywhere

  • Exact arithmetic only. The simulation uses + − × ÷ and sqrt, which IEEE-754 specifies exactly. No log, exp or sin, whose last bits differ between browsers.
  • Own SHA-256. A plain-JS implementation, not crypto.subtle, so the page works from file://. It's standard SHA-256: check it against any other tool.
  • Decided at GO. The animation is playback. Nothing during it can change the outcome; you can even close the tab.

What the server checks

The server distributes race parameters; it never decides an outcome. These rules stop it being used to swap a race after the audience has spoken.

  • Every commitment is logged with the time it was published, withdrawn, raced or abandoned, readable by anyone at /api/commitments.
  • A real race is refused unless its commitment is the one in the lobby, has been public for 20 s or more, and hasn't already been raced. One commitment, one race.
  • A race is refused unless the secret, roster, length and source reproduce the commitment, the roster matches the one in the lobby, and the seed is SHA-256(secret | audience value).
  • A receipt is refused unless it matches the race viewers were shown. The server attaches its timeline as receipt.server.
  • A real race replaced or cleared before its winner finishes is logged as cut short, and the next race carries that record as abandonedBefore.
  • Every operator action needs the operator key; the watch link is read-only.

What each viewer's page checks

The operator runs the server, so each viewer's own device keeps its own record. This is the stronger check.

  • When it first showed each commitment, and whether one was withdrawn (“commitment replaced” alert).
  • That the lobby roster reproduces the sealed hash, and how many entries each name has.
  • Before playing: the secret reproduces the commitment it saw, the roster matches the lobby, and the seed is correct. Otherwise the race is refused.
  • Which race it actually played: seed, roster, length and winner. A receipt for any other race fails.
  • Whether a race it was watching was stopped before its winner finished.

Races run back to back after each one finishes (one per prize, say) are not flagged as cut short.

Verifying a receipt

A receipt contains the format, commitment, secret, entropy source, audience value, final seed, race length, roster, roster hash, results hash, top 10 and the operator's build fingerprint, plus the server's timeline when the race ran live. Every field is required.

The Verify tab

Recomputes the whole race from the receipt, without talking to any server, and reports each check at one of three levels:

  • ✓ passed: the commitment, seed, roster hash, results, winner and top 10 all reproduce, and the names and audience value are in cleaned form.
  • ⚠ question to ask: no commitment entered to compare, a viewer who joined late, a commitment replaced or a race cut short just before, a different build, or an old format 1 receipt.
  • ✗ failed: anything that doesn't reproduce, a commitment different from the one you saw, one shown for under 20 s, a practice race, or a receipt for a different race from the one your device played.

Entering the commitment you saw before the race is the check that matters most. A receipt can only prove it agrees with itself; matching it with what was on screen before the audience spoke proves nothing was swapped. Compare the whole value, not the first few characters.

Without this page

  • verify.js is a standalone Node script, with no packages and no network: node verify.js receipt.json --saw <commitment>. It runs the same checks, apart from the live-viewing record only a watching browser has. Its race code is a verbatim copy of this page's, and it checks its own SHA-256 against Node's.
  • Build fingerprint. A hash of the race code's own source and its tuning constants. The page, verify.js and the receipt all report it, so a matching fingerprint means the same code ran.
  • By hand. Rebuild the commitment from the receipt's fields with any SHA-256 tool (see the formulas above). The Verify tab has a scratch pad.
  • The self-check badge is a tripwire, not proof. It notices if an extension patched the race code, but a hostile page could fake it too. Recomputing on a second, clean device is the real guarantee.

Watching live

  • Nothing is streamed. The server sends the seed, roster, length and one start time; every screen recomputes the identical race itself. One small message per race, however many people watch.
  • Shared clock. Each screen measures its offset from the server's clock, and playback time is server time − start time. Screens can't drift apart, late joiners land on the right moment, and a backgrounded tab catches up.
  • Countdown. 30 seconds on every screen before the gun, so people have time to open the link.
  • Remote viewers. share-public.sh opens a temporary public tunnel; nothing is exposed until it runs, and it closes on Ctrl-C.

Running it for an audience

  1. Paste the names and pick the length. Fix any look-alike warnings.
  2. Write down exactly where the audience value will come from.
  3. Hit Generate secret seed. Show the fingerprint on the big screen and post it in the event chat. Let people photograph it.
  4. Wait at least 20 seconds, then collect the audience value from the named source. Type it in where everyone can see “Hashed as”.
  5. Start the race. Every screen checks it before the gun.
  6. Hit Reveal and hand out the receipt. Anyone can verify it on their own device, offline.

What software can't enforce

These depend on how a race is run, not on code. They are the remaining ways a determined operator, or someone working with one, could tilt a race.

  1. Viewers run the page the server sends them. A dishonest server could send a page whose checks always pass. Publish index.html and verify.js, with their SHA-256 hashes, somewhere the operator doesn't control before the event, and have at least one independent person verify each receipt with that copy.
  2. The entropy source must leave no choice. The software seals the description; only people can judge whether it allowed a pick. “A word from the audience” lets the operator choose among several.
  3. Use more than one contributor. One planted accomplice shouting a pre-agreed word lets the operator work out the result in advance. Combine values from several people.
  4. Compare the whole commitment. Matching only the first few hex characters can be faked in seconds.
  5. Make sure everyone saw the same thing. An operator who controls the server could show different viewers different commitments. People in the room, remote viewers and the chat should compare.
  6. Treat warnings as questions. “Commitment replaced”, “race cut short” and “joined late” all have innocent explanations, but only people can tell. Ask at the time.

A patient operator could re-commit after the audience speaks and wait out the 20 seconds. Every screen shows a “commitment replaced” alert and the verifier warns, but only the audience knows whether the swap came before or after they spoke.

Cosmetic only

None of these enter the seed, the simulation or the receipt, so a race verifies the same whichever is used.

  • Racer type: pugs, sloths, ducks, boomers or turtles, each with its own backdrop and commentary. Slow themes look slow through camera distance and gait, not by changing the race.
  • Views: everyone, leaders or 1st place, with zoom, pan and “find a pug” for large fields.
  • Sound: synthesised live, driven by events that have already been decided.
  • Podium, confetti and results post: drawn after the result, seeded from the race seed rather than Math.random().

Known limits

  • A viewer with developer tools can work out the winner the moment the race is announced, since the race is computed on their device. This doesn't affect fairness, only suspense.
  • Name cleaning flattens some emoji sequences (joined emoji and subdivision flags), and names ending in #<digits> are shown as # <digits>.
  • Receipts made before the current build show a build-mismatch warning; their results still reproduce.
  • The free tunnel URL changes every run.

The 100 racer skins

Skins are drawn procedurally from a fixed table — skin #47 is always the same pug, on every machine. Coat, mask, patches, ears, eyes, collar and accessory are combined so that no two of the 100 are alike.
